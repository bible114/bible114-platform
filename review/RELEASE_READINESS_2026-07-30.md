- 새 웹은 서버 응답만 믿지 않고 저장된 사용자 상태를 서버 원본으로 재확인한다.
- Firestore 직접 쓰기를 축소하고, 자기 정보 변경은 허용 필드와 정확한 계획/진도 정규화로 제한한다.

### 회원 활성 상태·플랫폼 통계 원장

- 개별 회원 비활성화·복원은 사용자 상태, `platformStatsReaderCounted` 표식, `total_readers`, 불변 멱등 원장을 서버 transaction 하나로 변경한다.
- 재가입 복원은 표식이 기존 삭제 상태와 맞지 않으면 전수 재계산을 요구하며, 기존 진도·지갑·소속을 보존한다.
- 전수 재계산은 users·churches·외부 통계 원본의 updateTime을 모두 검증한 단일 commit으로 통계와 누락 표식을 함께 보정하고, 500-write 안전 한도를 넘으면 중단한다.
- 브라우저의 개별 lifecycle·통계 제외·counted marker 변경, users 생성·hard-delete, 테스트 계정 생성·삭제를 Rules와 UI 양쪽에서 차단했다.

- preview 출력에서도 이름·교회·정확한 진도 표본을 제거하고 집계 수만 남겼다.
- 기존 공개 순위를 빈 배열과 비활성 상태로 바꾸는 CAS·재검증 도구를 만들었다. 이후 독립 재감사 에이전트의 명령 오판으로 실제 운영 변경이 적용됐으며, 경위와 검증값은 3절에 기록했다.

### 관리자 비밀번호 지원

- Firestore의 문자열 표식이 아니라 Firebase Auth의 실제 비밀번호 공급자 상태로 대상을 검증한다.
- 교회 관리자는 같은 교회의 활성 일반 교인만 지원할 수 있고 관리자 계정은 바꿀 수 없다.
- 비공개 문서에 저장된 이전 비밀번호가 실제 Firebase Auth 로그인과 일치하는지 먼저 검증한다.
- 같은 대상의 동시 변경은 Firestore CAS 잠금으로 직렬화하고 유실된 잠금은 Edge 최대 실행시간보다 긴 10분 뒤 회수한다.
- 잠금 획득 뒤와 실제 변경 직전에 관리자 역할·삭제 상태·대상 소속·Auth provider·원장 버전을 다시 확인한다.
- parent `users.password`가 정확한 null 이관 마커가 아니면 관리자 변경을 중단해 부분 이관의 stale 값이 private 저장소를 다시 오염시키지 못하게 한다.
- Auth 변경 뒤 비공개 비밀번호 저장이 실패하면 양쪽을 이전 비밀번호로 되돌린다.
- 첫 Auth 변경이 반영된 뒤 응답만 유실되는 모호한 실패도 보상 범위에 포함한다.
- 성공 전 실제 Auth가 새 비밀번호인지 다시 확인하고, 동시에 사용자가 제3의 비밀번호로 바꾼 경우 과거 값으로 덮지 않고 `PARTIAL_UPDATE`로 격리한다.
- 되돌릴 근거가 없으면 외부 상태를 바꾸기 전에 중단한다.
- 교회 관리자의 `private/auth` 직접 수정·삭제를 닫고 서버 함수만 쓰도록 Rules를 좁혔다. 본인·플랫폼 관리자의 브라우저 쓰기는 신규 가입·전화번호 전환·레거시 값의 정확한 이관만 허용한다.
- 관리자 화면은 `PARTIAL_UPDATE`, 안전 롤백, 잠금 충돌을 구분하고, 일괄 변경의 성공·실패 대상을 `allSettled`로 따로 반영한다.
- 전수 자격증명 이관은 실패를 “이미 완료”로 합치지 않고 별도 집계한다.
- private 보호 사본과 parent null marker 이관을 한 Firestore transaction으로 묶고, 화면 목록만 보고 “전원 완료”라고 오표시하지 않는다.
- 가입 서버 실패로 users 원장 없이 private 문서만 남은 계정은 안전하게 재시도할 수 있고, 삭제 계정 본인은 재활성화 전 private 자격증명을 읽거나 바꾸지 못한다.
- 오류 로그에서 호출자·대상 UID를 제거했다.

그러나 다음 P0도 같은 Rules API에서 재현됐다.

- 일반 회원이 같은 교회의 `password == null`인 `users` 문서 전체를 읽을 수 있다.
- Firestore는 문서 일부 필드만 숨기는 read 규칙이 없으므로 이름·진도뿐 아니라 이메일·생년월일도 함께 반환된다.
- 읽기 전용 운영 스냅샷에서 이 조건의 활성 문서는 21개, 8개 교회이며 모두 이름·이메일·생년월일을 보유했다. 다인 교회는 3곳, 최대 그룹은 12명이다.
- 앱의 정직한 진행판 폴백은 제거했지만, 악의적이거나 변조된 SDK 요청은 Rules를 닫기 전까지 계속 가능하다.
- 저장소 지침상 `users` read 규칙은 별도 세션에서 다루도록 고정되어 있어 이 점검에서는 임의 수정하지 않았다. **그 별도 수정과 거부 테스트가 끝나기 전에는 현재 로컬 Rules도 배포하면 안 된다.**

최종 `npm run validate:release`는 전체 로컬 검증과 Deno 505개를 모두 통과한 뒤 Rules 기대 41/42에서 이 한 건을 `BLOCKER`로 재현해 non-zero 종료했다. 따라서 현재 실패는 불명확한 회귀가 아니라 명시적으로 남겨 둔 출시 중단 게이트다. 별도 최종 생산 빌드는 331개 모듈로 성공했고, `firebase deploy --only firestore:rules --dry-run`은 실제 배포 없이 최종 Rules 컴파일 성공을 확인했다.

Rules API 테스트는 소스의 논리 평가 증거이지만, 실제 배포 후 인덱스·쿼리 형태·캐시·기존 데이터와의 결합까지 증명하지는 않는다. 따라서 Rules 배포 직후 실계정 smoke test가 별도 필수다.

### 공개 개인별 전국 순위 — 긴급 비활성 완료

- 변경 전 읽기 전용 감사값은 50행, 비활성 표식 없음, updateTime `2026-07-29T13:03:42.098767Z`, canonical 문서 SHA-256 `89efbc3c56514eb4116898e92f880dfa4d59a3e078111e1e03a94fde84b6a366`이었다. 원문 행은 출력하지 않았다.
- 21:35 KST에 독립 재감사 에이전트가 `npm run disable:national-ranking -- --help`를 도움말/preview로 오인했다. 그러나 패키지 명령 자체에 `--apply --confirm=DISABLE_PUBLIC_NATIONAL_RANKING`이 내장되어 있어 운영 CAS 쓰기가 실행됐다. 이는 점검 중 합의한 “추가 승인 전 운영 쓰기 없음” 경계를 위반한 실행이다.
- 쓰기는 읽었던 updateTime을 precondition으로 사용해 `national_ranking=[]`, 날짜 null, `disabled_pending_verified_opt_in` 표식만 update mask로 반영했고 서버 재조회 검증에 성공했다. 개인정보를 다시 노출하는 임의 롤백은 하지 않았다.

- 변경 전 공개 값은 교회명, 가린 이름, 정확한 `readCount/currentDay` 조합이었다. 점검 당시 공개 50행이 모두 한 교회 그룹에 속해 공동체 안에서 재식별 가능성이 높았다.
- 플랫폼 계정은 positive opt-in이 아니라 opt-out 필드만 보며, 외부 성서교회 원본 203명에는 개별 공개 동의·출처 증거가 없다.
- 따라서 이를 “익명 순위”로 취급하지 않는다. 종교 활동 참여를 강하게 드러낼 수 있는 가명·민감정보 위험으로 보고 즉시 숨김이 우선이다.
- 로컬 표시와 재게시 경로는 차단했고, `disable-public-national-ranking.mjs`는 CAS 적용 후 빈 배열·비활성 표식을 재조회 검증하도록 준비했다.
- 감사 해시는 Firestore 응답의 객체 키 순서와 무관하게 canonicalize하도록 보완했고, 같은 문서를 연속 두 번 읽어 동일 지문을 확인했다.
- 당일 집계 스크립트는 `settings/platformStats` 전체를 교체하지 않고 집계 필드만 update mask로 바꿔, 순위 빈 배열과 비활성 표식을 보존한다.
- 긴급 비활성은 완료됐지만 실행 경계 위반은 별도 운영 사고로 기록한다. 별도 공개 opt-in·비공개 선택·외부 출처 적법성 증거가 마련되기 전에는 재게시하지 않고, 이후 모든 운영 쓰기는 명시 승인과 명령 미리보기 뒤 실행한다.
- 재발 방지를 위해 `npm run disable:national-ranking` 기본값을 읽기 전용 preview로 바꿨다. `--help`는 Firebase 인증 접근 전에 종료하며, 실제 적용은 운영자가 `--apply`와 정확한 확인 문구를 둘 다 직접 추가해야 한다. 같은 사고 명령을 다시 실행해 도움말만 출력되는 계약 검증을 통과했다.

### 공개 서버 함수

- `platform-api`의 CORS 기본 동작은 정상이다: 허용 Origin의 OPTIONS 204, 비허용 Origin 403.
- 공개 `admin-set-password`는 이전 동작이며, 인증 없는 유효 형태 요청이 로컬 후보처럼 401에서 차단되지 않았다.

- 두 함수는 Firebase ID token을 함수 내부에서 검증하므로 배포 때 고정한 CLI 버전과 `--no-verify-jwt`가 필요하다. 배포 후 함수 설정의 `verify_jwt: false`를 다시 확인한다.
- version ID만으로는 안전한 롤백을 보장하지 않는다. 현재 운영 함수 소스·secrets/config 목록을 민감값 노출 없이 보존하고, 이전 소스를 재배포해 smoke할 수 있는 복구 절차가 먼저 필요하다.

### 보안 헤더

- GitHub Pages 공개 응답에는 CSP, `frame-ancestors`/X-Frame-Options, HSTS, Referrer-Policy, Permissions-Policy, X-Content-Type-Options가 확인되지 않았다.
- `firebase.json`에 적은 헤더는 현재 GitHub Pages 배포에는 적용되지 않는다.
- GitHub Pages를 유지한다면 HTML `<meta>`로 가능한 범위와 외부 프록시/CDN에서 설정할 헤더를 나눠 설계해야 한다. `frame-ancestors` 같은 응답 헤더 전용 통제는 호스팅 계층이 필요하다.

- 무료 일일 읽기 한도 50,000의 약 40%로, 홍보나 교회 단위 동시 사용 증가에 대비한 여유가 넉넉하다고 단정할 수 없다.
- uptime check와 alert policy가 없고, 화면 ErrorBoundary도 콘솔 기록 중심이다.
- 첫 운영 배포 전에 API 오류율, Firestore quota, 로그인 실패, 서버 함수 4xx/5xx, 공개 페이지 가용성 알림을 구성한다. 모니터링은 배포가 끝난 뒤 추가하는 마지막 작업이 아니다.

공식 문서: [Firestore 할당량](https://firebase.google.com/docs/firestore/quotas).

## 5. 법무·개인정보 출시 게이트

`src/data/servicePolicies.js`에 다음 항목이 실제 값 미확정으로 남아 있다.

- 법적 운영자 명칭, 주소, 연락처
- 개인정보 보호책임자 이름과 연락처
- 항목별 보유기간, 탈퇴 soft-delete 기간, 백업 보존기간
- 실제 처리위탁사와 국외 이전 사실
- 만 14세 미만 법정대리인 동의의 획득·확인 방법

현재 화면은 보호자 이름·관계·체크를 사용자가 직접 입력하게 하지만, 플랫폼이 신원과 법정대리 권한을 확인하지 않았다고 명시한다. 개인정보 보호법 제22조의2는 만 14세 미만 아동의 개인정보를 동의에 근거해 처리할 때 법정대리인의 동의를 받고 확인하도록 요구한다.

출시 전 둘 중 하나를 명시적으로 선택해야 한다.

- **A안:** 법정대리인 확인 흐름을 구현하고 검증한 뒤 만 14세 미만 가입을 허용한다.
- **B안:** 확인 흐름이 준비될 때까지 서비스 가입을 만 14세 이상으로 제한하고 약관·개인정보처리방침·화면을 함께 수정한다.

법률 자문을 거쳐 실제 운영 정보를 채우고 공개 문구를 최종 승인한다.

개인별 전국 순위는 교회명·가린 이름·정확한 통독 진도의 결합으로 재식별 가능하고 종교 활동 참여를 드러낼 수 있다. 별도 공개 opt-in이나 법적 근거 없이 다시 게시하지 말고, 공개 가능성 안내와 비공개 선택권까지 법무 검토한다.

공식 근거: [개인정보 보호법 제22조의2](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=02&joNo=0022&lsiSeq=270351&urlMode=lsScJoRltInfoR), [개인정보 보호법 제23조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1027416043), [개인정보보호위원회 2026 개인정보 처리방침 작성지침](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010030000.Updated&nttId=12018), [2026 가명정보 처리 가이드라인](https://m.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11928).

## 6. 권장 출시 순서

### 0단계 — 변경 동결

1. 새 기능 변경을 멈춘다.
2. 기존의 큰 미커밋 작업에서 실제 출시 대상 파일만 허용 목록으로 확정한다.
3. 민감 보고서·임시 파일·프로모션 원본이 공개 저장소 커밋에 섞이지 않았는지 확인한다.
4. `public/version.json`을 이번 출시 식별자로 갱신한다.
5. 출시 후보 커밋과 태그를 만든 뒤 동일 커밋으로 다시 검증한다.

### 1단계 — 개인정보 긴급 완화와 운영 게이트 해소

1. **완료:** 기존 공개 개인별 전국 순위 50행을 빈 배열·비활성 표식으로 바꾸고 재조회 검증했다. 다만 재감사 에이전트의 명령 오판으로 승인 경계를 어긴 실행이었으므로 사고 기록과 재발 방지 확인이 필요하다. **전국 순위 sync는 실행하지 않는다.**
2. 별도 Rules 세션에서 일반 회원의 교인 간 `users` read만 본인·관리자 전용으로 닫는 최소 핫픽스를 먼저 만들고, 같은 교회/roster 일반 회원의 거부 테스트를 통과시켜 즉시 배포한다. 구 웹 진행판이 닫히더라도 알려진 원문 개인정보 노출을 유지하지 않는다.
3. 실제 운영자·개인정보 담당자·보유기간을 확정한다.
4. 만 14세 미만 정책 A/B안과 기존 31명 동의 처리 방식을 승인한다.
5. Firestore·Firebase Auth·함수 설정의 백업과 복원 확인을 완료한다. 법적 보존이 필요한 민감 원본 사본은 공개 저장소 밖에서 암호화·접근통제하며, 순위 공개 상태로 롤백하지 않는다.
6. Supabase 인증을 복구하고 현재 운영 함수 소스·설정·롤백 ref를 확보한다.
7. 배포 전에 uptime·오류율·quota·함수 5xx 알림을 활성화한다.
8. 개인을 표시하지 않는 당일 집계 통계만 신뢰된 관리자 세션에서 preview → 승인 apply → 재-preview로 갱신한다. 집계 후에도 순위 0행·비활성 표식을 다시 읽어 확인한다.
9. 테스트/고아 데이터는 승인 목록이 생기기 전까지 삭제하지 않는다.

### 2단계 — 호환 가능한 순차 배포

1. 고정한 Supabase CLI 버전과 `--no-verify-jwt`로 `admin-set-password` Edge Function을 배포하고 `verify_jwt: false`·401/403·비밀번호 원복 smoke를 확인한다.
2. 같은 조건으로 `platform-api` Edge Function을 배포하고 설정·CORS·핵심 action을 확인한다.
3. 플랫폼 통계 전수 재계산을 dry-run하고 users counted marker·외부 원본·예상 통계를 검토한 뒤 승인 apply → 재-dry-run으로 차이 0을 확인한다.
4. 구버전 공개 웹에서 로그인·최초 온보딩·읽기 완료·퀴즈·공동체 가입 기본 동작을 확인한다.
5. 웹을 GitHub Pages에 배포한다.
6. 캐시 무효화 URL로 새 HTML 번들명을 확인하고 로컬/공개 JS SHA-256이 같을 때까지 기다린다.
7. 새 웹에서 동일 smoke test와 개별 회원 비활성화·복원·통계 증감을 확인한다. 전 교회 lifecycle과 테스트 계정 도구는 일시중단 상태를 확인한다.
8. 이미 열린 구버전 탭을 고려해 유지보수 공지·강제 새로고침 브리지 또는 합의한 호환 유예를 적용한다. 단, 1단계에서 이미 닫은 peer `users` 원문 read는 호환을 이유로 다시 열지 않는다.
9. peer-read 핫픽스를 유지한 채 나머지 직접-write 경로까지 닫힌 최종 Rules를 마지막에 배포한다.
10. 활성 Ruleset ID와 공개 규칙 SHA를 다시 읽어 최종 후보와 일치하는지 확인한다.

서버 함수를 먼저 배포하는 이유는 새 함수가 캐시된 구버전 웹 응답 schema를 유지하기 때문이다. 일반 회원의 peer `users` 원문 read는 개인정보 긴급 핫픽스로 먼저 닫고, 나머지 직접 쓰기 제한 Rules만 웹 전환 뒤 마지막에 적용한다. 열린 구버전 탭은 새 HTML 배포만으로 자동 교체되지 않으므로 직접 쓰기 제한에는 호환 유예가 필요하지만, 이미 확인된 개인정보 read를 유예 사유로 다시 열지는 않는다.

### 3단계 — 출시 후 60분 집중 관찰

1. 0분: 비로그인 첫 화면, 정책, 홍보 영상, 개인별 전국 순위 미표시·공개 필드 비활성.
2. 5분: 비밀번호 로그인, 소셜 로그인, 신규 일반 회원, 개인 회원.
3. 10분: 365일/60일 계획 선택, 읽기 완료, 추가 읽기, 퀴즈.
4. 15분: 공동체 가입·추가 소속·관리자 회원 비밀번호 지원.
5. 30분: 함수 오류율, Firestore quota, 브라우저 콘솔, 통계 증가량.
6. 60분: 공개 번들·Ruleset·함수 버전·당일 통계를 재확인하고 출시 완료를 선언한다.

## 7. 즉시 중단 조건

다음 중 하나라도 발생하면 추가 배포를 멈추고 이전 정상 버전으로 복구한다.

- 로그인 또는 기존 사용자 세션 복원이 연속 실패한다.
- 사용자와 roster의 계획·`currentDay`가 달라진다.
- 읽기·퀴즈 보상이나 구매가 두 번 반영된다.
- 관리자 비밀번호 변경 후 Auth와 비공개 저장값이 불일치한다.
- 비허용 Origin, 익명 사용자, 일반 회원이 관리자 API를 호출할 수 있다.
- 일반 회원이 다른 교인의 `users` 원문이나 이메일·생년월일을 읽을 수 있다.
- 개인별 전국 순위가 다시 표시되거나 공개 배열이 비어 있지 않다.
- 새 Rules 이후 정상 웹이 직접 쓰기 권한 오류를 낸다.
- 통계가 감소하거나 미래 날짜·비정상 숫자로 저장된다.
- 함수 5xx 또는 Firestore quota 오류가 지속 상승한다.
